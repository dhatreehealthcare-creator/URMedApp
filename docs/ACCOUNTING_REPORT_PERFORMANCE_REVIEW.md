# Accounting and report performance review

## Current review

- Accounting statement queries use indexed date/vendor/party columns and aggregate only the selected period. The `ledger_entries_vendor_date_idx`, `ledger_entries_party_date_idx`, `accounting_opening_balances_vendor_date_idx`, and report-specific vendor/date indexes are the primary access paths.
- Stock and sales reports use bounded date/page filters. Sales uses invoice/event evidence and returns rather than mutable order totals.
- Home-delivery distance and SLA calculations intentionally remain bounded to 5,000 candidates because precise coordinates are private and distance is derived in application memory. This report should be moved to a materialized daily fact table if volume exceeds that bound.
- XLSX exports are minimal Office Open XML workbooks generated without external network access; PDF exports are deterministic text reports generated by `pdf-lib`. They are operational exports, not statutory filing artifacts.

## Benchmark policy

The repository includes `node scripts/benchmark-report-plans.mjs` as a deterministic local smoke check for the ledger and order report predicates. It records the observed SQLite plans in `/tmp/urmed-report-query-plans.json` and is intentionally not treated as the production-scale benchmark.

Before production cutover, run `EXPLAIN QUERY PLAN` for each report against a representative anonymized D1 snapshot and record execution time at 10k, 100k, and 1m ledger/order rows. Any full scan on date/vendor predicates must receive a reviewed index or a bounded archival strategy. Hosted D1 performance cannot be inferred from local SQLite alone.

## Accounting approval gate

The recognition and closing rules in `docs/ACCOUNTING_RECOGNITION_AND_CLOSING_POLICY.md` are implementation defaults. An accountant must approve them, especially inventory valuation, accruals/depreciation, GST period treatment, opening balances, and post-close adjustments, before statutory or management statements are relied upon.
